## 1. 项目定位与设计意图

### 1.1 一句话定义

`emotion_agent` 是一个**外挂式情绪控制器**：在用户输入与 LLM 生成之间插入一条 18 步的计算链路，把内部情绪状态（4 维）与自控强度（标量）翻译成一段自然语言"心理独白"，拼进 prompt，让 LLM 的回复语气由内部状态自然驱动，而非在 prompt 里硬写人设。

### 1.2 设计出发点

常规做法是在 system prompt 里写"你是一个有情绪的 AI"。本项目认为这种做法的问题在于：**情绪状态没有被真正计算出来**，因此无法随对话历史演化，也无法解释为什么同样的输入在不同轮次会得到不同语气。

本项目的做法是把情绪当作一个**带记忆的递归状态**：

- 情绪有惯性：`E_raw = LAMBDA * E_prev + released_impact + ...`，上一轮的情绪影响下一轮
- 自控有强化：`w_PFC_new = RHO * w_PFC + DELTA * I_inhibit`，抑制强度会自我累积
- 危险有记忆：`danger_score` 写入 `EventNode`，下次相似事件会通过海马体匹配把历史危险值唤起
- 习惯化存在：反复遭遇同类事件时 `HabituationSignal` 上升，情绪释放率同步上升

### 1.4 项目的真正目标

本项目不是"给 AI 加个人设"。它的目标是：**在 AI 外面造一个"真实的人"，而不是一个"演得像人"的东西**。

区别在哪：

- **演得像人（模仿）**：给它一段提示词（"你是一个有情绪的 AI"），让它演出来。这叫**导演**。
- **真实的人（自主）**：它真的有情绪、有记忆、有自己的念头。它的回应不是"调取剧本"，而是"带着自己的过去，生出一个当下的念头"。这叫**造物**。

所有者在项目中途完成了一次**哲学转型**：从"我想做一个像某人的 AI"，转到"我想做一个真实的人"。

**对分析者的意义**：当前所有技术决策，都要在这把尺子下衡量。判断一个改动该不该做，标准不是"能不能让指标好看"，而是"它让系统更像个活物，还是更像一台表演机器"。按这把尺子看，很多"看起来是优化"的改动实际上是倒退——例如把情绪表达做得更平滑、更像模板，反而离"真实"更远。

### 1.5 原始设计参考

项目的灵感来自另一位作者的一套 AI 记忆系统设计，其架构分三层：

| 层 | 职责 | 在原始设计中的作用 |
| --- | --- | --- |
| **石海** | 存 + 潜伏 + 唤起候选 | 记忆的仓库 |
| **星光** | 从候选里筛"谁进入意识" | 注意力筛选 |
| **星流** | 把选中的整合成思考 | 认知生成 |

**当前代码与原始设计的对应关系**（重要）：

| 原始层 | 当前代码对应 | 状态 |
| --- | --- | --- |
| 石海 | 散落在 `memory_graph` + `archiver` + `raw_log` 三处 | **未统一**，三处各自存储 |
| 星光 | `xinguang.competition_score` + `hippocampal_evaluator` | **命名错位**：代码里叫"海马体"的模块，实际干的是"星光"的活 |
| 星流 | —— | **完全不存在**，M3 之后要新建 |

**这意味着当前代码的命名与设计概念存在系统性错位**。代码里的"海马体"（hippocampus）承担的是原始设计中"星光"（注意力筛选）的职责，而真正的"石海"概念被拆散在三个文件里。

M3 后续重构会重新命名并统合这些概念，但**本版本不动**——命名重整属于结构变更，需单独裁决。

### 1.6 两个里程碑的真正意义

**T3（V4.5）：把 `event_parser` 的 8 维 hash 嵌入换成 1024 维 BGE 语义嵌入。**

- **效果**：系统第一次"听懂话"
- 之前："你真蠢"和"你太笨了"被当作两件无关的事（MD5 hash 无语义，相似度趋近于随机）
- 之后：系统知道它们是同一类
- **解决的是"记忆检索"这一侧**

**T24（V4.6）：让召回记忆的 `emotion_value` 影响本轮 `D_slow`。**

- **效果**：记忆第一次"参与评估"
- 之前：记忆存进去、能召回，但召回的值只看不用
- 之后：第 7 轮起，召回的情绪值真的改变了危险判断（实测 `D_slow` +0.072）
- **解决的是"记忆 → 情绪"这条链**

**但两个里程碑都还没解决"情绪评估语义化"**——当前 `x` 里，1024 维 embedding 只被压成 **1 个标量**（`x[0]`），且该标量因`M_prev` 未回写而恒为 0（见 12.1）。1024 维语义信息对情绪评估的贡献实际接近于零。

这是下一个大重构的战场，详见 15.1。

## 3. 整体架构与数据流总览

### 3.1 顶层数据流

```
用户输入 (raw_text)
      │
      ▼
┌─────────────────────────────────────────────────────────┐
│                18 步主链路（pipeline.py）                │
│  1事件拆解 → 2 特征编码 → 3 心光预算 → 4 海马体        │
│  → [T24 注入点] → 6 快通路 / 7 慢通路（并行分支）      │
│  → 8 情绪释放 → 9 情绪加点 → 10 拦截 → 11 策略          │
│  → 12 状态翻译 → 13 prompt → 14 LLM 生成               │
│  → 15 回写识海 → 16 写日志 → 17 写缓冲区 → 18 归档      │
└─────────────────────────────────────────────────────────┘
      │                    │
      ▼                    ▼
  LLM 回复            记忆包（满6 轮）
                           │
                           ▼
                    下一轮读取侧召回
```

### 3.2 三个计算分支

链路内部实际存在三条并行分支，各自吃不同的输入：

| 分支 | 输入 | 参数 | 产出 | 特点 |
| --- | --- | --- | --- | --- |
| 快通路 | `x_fast`（4 维，仅字符串启发式） | `w_f`(4)、`b_f` | `D_fast` | 不依赖嵌入，质量稳定 |
| 慢通路 | `x + ReframedContext`（8 维）、`M`（1024 维） | `w_s`(8)、`u_s`(1024)、`W_v`(2,8)、`U_v`(2,1024) | `D_slow`、`V`(2 维) | 依赖嵌入，是主要计算量 |
| 记忆通路 | `archiver` 中的记忆包 | 无参数 | `emotion_value` | T24 起影响慢通路 |

快慢分离的设计意图 `[推断]`：让"即时反应"（快）与"深度评估"（慢）用不同的信息通路，避免嵌入质量拖累基础响应。`x_fast` 完全由字符串启发式构成（危险词命中、正负词计数、标点数量），与 `event_embedding` 无关。

## 4. 18 步主链路逐环节详解

以下每一节包含：**做什么 → 怎么处理 → 输入输出 → 往复关系 → 交给下一部分什么**。

### 步骤 1 · event_parser.parse()

**做什么**：把一句原始文本变成结构化的 `EventNode`。

**怎么处理**：
1. 生成 `event_id`（时间戳取模 6 位）
2. 调 `_embedder.encode(raw_text)` 得1024 维语义向量。`embedder` 是模块级单例，BGE 为懒加载（构造本身轻量，首次调用才载入模型）
3. 关键词匹配提取 persons/tasks，各 10 个提示词。`nodes` 字典里 `topic`/`state`/`relation` 三个键恒为空列表
4. 五个标量字段（importance、emotion_weight、unfinished、danger_score、event_severity）由调用方传入，此处不计算

**输入**：`raw_text` + 五个占位标量
**输出**：`EventNode`
**往复**：无状态写入。但它是 `memory_graph.add()` 的写入对象，是记忆回路的起点
**交给下游**：整个 `event` 对象 → 步骤 2（算特征）、步骤 4（海马体匹配）、步骤 15（写回识海）

**注意点** `[代码]`：`hash_to_8d` 函数已标记弃用，仅保留供 `scripts/probe_embedder.py` 向后兼容比对使用，主链路不调用。`config.py` L2 与 L19 记录了对应限制。

### 步骤 2 · feature_encoder.encode()

**做什么**：从 `event` 与状态中提取两个特征向量——慢通路的 `x`(8 维) 与快通路的 `x_fast`(4 维)。

**怎么处理**：

`x_fast`（4 维，纯字符串启发式）：
| 分量 | 计算方式 | 值域 |
| --- | --- | --- |
| `x_fast[0]` | 命中 `DANGER_KEYWORDS` 则 1.0，否则 0.0 | {0, 1} |
| `x_fast[1]` | `(负词数 - 正词数) / (正词数 + 负词数 + 1e-6)` | [-1, 1] |
| `x_fast[2]` | `!！?？` 总数 ÷ 3，上限 1.0 | [0, 1] |
| `x_fast[3]` | **硬编码 0.0** | {0} |

`x`（8 维）：
| 分量 | 计算方式 | 备注 |
| --- | --- | --- |
| `x[0]` | `safe_cosine(event_embedding, M_prev)` | **恒为 0**，见 12.1 |
| `x[1]` | 当前人物集与历史人物集的重合比 | 分母 `len(cur_persons) + 1e-6` |
| `x[2]` | 有 task 则 1.0，否则 0.0 | |
| `x[3]` | 直接复用 `x_fast[1]` | 共用分量 |
| `x[4]` | `event_severity` 直传 | |
| `x[5]` | `HabituationSignal_prev` | **恒为 0**，见 12.1 |
| `x[6]` | `B[1]` | 唤醒度 |
| `x[7]` | `B[2]` | |

**往复**：读 `M_prev`、`HabituationSignal_prev`、`B`、`memory_graph`，但**不回写任何状态**。纯函数式。
**交给下游**：`x` → 步骤 4（作为海马体输入）、步骤 7（慢通路）；`x_fast` → 步骤 6（快通路）

**注意点** `[代码]`：`x[1]` 的分母是 `len(cur_persons) + 1e-6`，不是并集大小，所以不是标准的 Jaccard 相似度，重合比可以大于 1。

### 步骤 3 · xinguang.update_xinguang_budget()

**做什么**：算出本轮"心光预算" `B_xg`，即当前有多少认知资源可用于记忆检索。

**怎么处理**：
```
arousal_penalty = 1 - |B[1] - 0.5| * 0.5
B_xg = clip(XG_BASE * B[0] * arousal_penalty, 0.1, 1.0)
```
`XG_BASE = 1.0`。含义是：能量 `B[0]` 越足、唤醒 `B[1]` 越接近 0.5（中等唤醒最优），预算越高。

**往复**：**纯函数，不改 B**。但它必须在步骤 6 之前算完——因为要用"回合开始时"的 B，若放到 fast_path 之后就会用到被本轮改过的 B，语义就错了。这是代码里唯一的严格顺序约束。
**交给下游**：标量 `B_xg` → 步骤 4

### 步骤 4 · hippocampal_evaluator.evaluate()

**做什么**：本模块是记忆检索与历史激活的唯一入口，也是链路最复杂的一步。

**怎么处理**：分两个分支。

**分支 A · 空历史（无候选）** `[代码]`：
直接返回固定值——`HistoricalResidual = 0.0`、`HabituationSignal = 0.0`、`ReframedContext = np.tanh(x)`、`M = np.zeros(1024)`、`M_text = "(无历史记忆)"`。`config.py` L8 已登记：三场景长期走这个分支。

**分支 B · 有候选**：
1. **筛候选**：算 `match_score`（两嵌入的余弦相似度），保留 `> MATCH_THRESHOLD(0.6)` 的历史事件
2. **算 residual与 H**：
   - `HistoricalResidual = mean(candidates.danger_score)` —— 这就是"记忆会放大危险"的实现
   - `weighted_count = Σ time_decay_weight(mem, now)`，其中 `time_decay_weight = exp(-Δdays / TAU_DAYS)`，`TAU_DAYS = 30`
   - `HabituationSignal = weighted_count / (weighted_count + 1)` —— 饱和函数，上限 1.0
3. **竞争打分**：对每个候选算 `competition_score`，由三部分相乘：
   ```
   activation = XG_W_ACT · [importance, recency, emotion_weight, relation, unfinished]
   match_val  = XG_W_MATCH · [语义相似度, 人物匹配, 时间匹配, 任务匹配]
   resource_fit = min(1, B_xg / (XG_COMPLEXITY_BASE * activation))
   score = activation * match_val * resource_fit
   ```
   注意 `resource_fit` 是分母含 activation 的形式——activation 越大的记忆越"贵"，超出预算时被打折
4. **取Top-K**：`K_XG = 3`，排序后取前三
5. **算 M**：`mean(TopK.event_embedding)` 再除以自身范数（归一化）
6. **算 ReframedContext**：`np.tanh(x + HistoricalResidual + HabituationSignal)`

**往复**：**读** `memory_graph`（唯一读 graph 的评估环节）。**不写** graph（写入在步骤 15）。
**交给下游**：`M`(1024 维) 与 `ReframedContext`(8 维) → 步骤 7；`M_text` → 步骤 12；`HabituationSignal` → 步骤 8 与 12

**注意点** `[代码]`：`relation_weight_term` 恒为 0.0，`person_match_term` 与 `task_match_term` 因 `EventNode.persons/tasks` 字段从不被赋值而恒为 0（config L18、L19 已登记）。所以 `match_val` 实际只有语义相似度与时间匹配两项在起作用。

### 插入点 · T24 · recalled_memory 注入

**位置**：步骤 4 之后、步骤 6/7 之前。

**做什么**：让归档记忆里的 `emotion_value` 影响本轮评估。

**怎么处理**：
```python
recalled_emotion_delta = 0.0
if st["recalled_memory"] is not None:
    recalled_emotion_delta = float(st["recalled_memory"]["emotion_value"])
ReframedContext = ReframedContext + recalled_emotion_delta
```

`ReframedContext` 维度跟随 `x`（8 维），标量广播到每一维。

**往复**：读 `st["recalled_memory"]`（由步骤 5 的读取侧填充），不写状态。
**交给下游**：加过的 `ReframedContext` → 步骤 7

**为什么接在这里** `[推断]`：`slow_path` 的公式是 `w_s @ (x + ReframedContext)`，这个括号是唯一能插手进慢通路又不改任何公式的位置。若接在 `x` 上会污染特征编码的语义边界，若接在 `slow_path.py` 内部则违反"不改 slow_path"的约束。

**已知副作用** `[实测]`：加法在 `tanh` **之外**，导致 `ReframedContext` 逐维绝对值可达 1.8，突破 `tanh` 原始值域 `[-1, 1]`。已登记为 L28，改进方向 T30（需改 `hippocampal_evaluator.py`，把加法挪进 `tanh` 内部）。

### 步骤 5 · 读取侧（archiver → decompressor）

**做什么**：查归档记忆，取出本轮要用的字段。

**怎么处理**：
1. `packages = archiver.get_packages()` 取全部记忆包
2. 若非空，取**最后一个**（最新归档的那个）
3. `decompressor.for_emotion_evaluator(pkg)` 返回 `{"emotion_value", "emotion_polarity"}`
4. 存进 `st["recalled_memory"]`

**往复**：读 `archiver`（内存中的记忆包列表）。**注意**：只取最新一个包，且只取 2 个字段。若开了 8 轮会话、第 6 轮归档，第 7、8 轮读到的是同一个包。
**交给下游**：`st["recalled_memory"]` → T24 插入点

**注意点** `[代码]`：`MEMORY_READ_ENABLED` 注释写"暂不影响 action"，这句注释在 T24 之后已经过期了——它现在确实影响 `D_slow`，只是实测未改变 action。

### 步骤 6 · fast_path.run_fast_path()

**做什么**：快通路，纯字符串启发式的即时反应。

**怎么处理**：
```python
D_fast = sigmoid(w_f @ x_fast + b_f)# w_f 是四个 0.5
if D_fast > THETA_FAST:            # THETA_FAST = 0.5
    B[1] = clip(B[1] + 0.3, 0, 1)      # 唤醒度直接 +0.3
return D_fast, B
```

**往复**：**这是唯一在评估期尝试修改状态的环节**。它直接原地修改传入的 `B` 数组的 `[1]` 位，而不是返回一个新数组。调用方 `pipeline.py` 拿到的是同一个对象引用（所以机制上跨轮是通的）。

**交给下游**：`D_fast` → 步骤 8；**改造后的 `B`** → 步骤 7（慢通路拿到的是改过的 B）

**注意点** `[实测]`：`w_f` 四个分量全是 0.5，`x_fast` 四分量中有一个恒为 0，所以 `D_fast` 的实际取值被压缩，实测**从未超过 `THETA_FAST = 0.5`**。因此 `B[1] += 0.3` 这个分支在8 轮实测中一次都没进入，`B` 在数值上保持 `[0.5]*4` 不变（见 9.2）。

### 步骤 7 · slow_path.run_slow_path()

**做什么**：慢通路，深度评估，产出两个核心量。

**怎么处理**：
```
z_s = w_s @ (x + ReframedContext)      # (8,) @ (8,) → 标量
    + u_s @ M                        # (1024,) @ (1024,) → 标量
    + v_s @ B                        # (4,) @ (4,) → 标量
    + ETA * w_PFC                # 0.3 * 标量
    + W_H * HabituationSignal# 0.5 * 标量
    + b_s                           # 0.0
D_slow = sigmoid(z_s)                 # (0, 1)

z_v = W_v @ (x + ReframedContext)     # (2,8) @ (8,) → (2,)
    + U_v @ M                        # (2,1024) @ (1024,) → (2,)
    + v_v * D_slow                   # 标量 * 标量
    + b_v                           # (2,)
V = sigmoid(z_v)                      # (2,) ∈ (0,1)^2
```

`V` 的两维语义 `[代码]`（由 `A_INIT` 第一行注释）：`V[0]` = 惩罚 → 负效价，`V[1]` = 奖励 → 正效价。

**往复**：只读，不写任何状态。
**交给下游**：`D_slow` 与 `V` → 步骤 8

**注意点** `[实测]`：这是计算量最大的一步，`u_s @ M` 是 1024 维点积。T24 改的就是这条公式里 `(x + ReframedContext)` 这个括号。

### 步骤 8 · emotion_releaser.run_releaser()

**做什么**：算情绪冲击，并按习惯化程度决定释放多少。

**怎么处理**：
```python
raw_emotion_impact = A_INIT @ V + b_E * D_fast     # (4,2)@(2,) → (4,)
release_rate = clip(BASE_RELEASE_RATE * (1 + HabituationSignal), 0, 0.9)
released_impact = raw_emotion_impact * (1 - release_rate)
```
`BASE_RELEASE_RATE = 0.3`，`b_E = [-1.0, 0.3, 0.1, 0.1]`。

语义：负面事件带来负效价（第一维，系数 -0.5），但`release_rate` 会随习惯化上升而增大（H=0 时释放 70%，H→1 时释放仅 30%），也就是说**老刺激的影响被逐渐压扁**。

**往复**：无。
**交给下游**：`released_impact`（4 维）→ 步骤 9；`release_rate` → 写日志

### 步骤 9 · emotion.run_emotion()

**做什么**：把本轮冲击累加到已有情绪上。

**怎么处理**：
```python
E_raw = clip(LAMBDA * E_prev + released_impact + C_INIT @ (B - B_INIT), -1, 1)
```
`LAMBDA = [0.9]*4`，`C_INIT` 是 (4,4) 矩阵，`B_INIT = [0.5]*4`。

**往复**：**读 `E_prev`**。理论上的跨轮往复，但见 12.2 —— `E_prev` 实际从未被写回。
**交给下游**：`E_raw`（4 维）→ 步骤 10

### 步骤 10 · intercept.run_intercept()

**做什么**：PFC（前额叶）自控层。负面情绪过强时压制表达。

**怎么处理**：
```python
neg_intensity = max(-E_raw, 0)                              # (4,) 只取负向
S_E = clip(w_e @ neg_intensity, 0, 1)                      # (4,)@(4,) → 标量
D_error = max(0, S_E - THETA_ERROR)                # 阈值 0.3
I_inhibit = clip(w_i * D_error + KAPPA * w_PFC + b_i, 0, 1)  # w_i=3.0, KAPPA=0.5
E_final = (1 - GAMMA * I_inhibit) * E_raw                  # GAMMA=0.6，按比例衰减
w_PFC_new = clip(RHO * w_PFC + DELTA * I_inhibit, 0, W_MAX)  # RHO=0.95, DELTA=0.1, W_MAX=2.0
```

**往复**：**读 `w_PFC`，吐 `w_PFC_new`**。这是链路里唯一显式的自反馈强化：`RHO=0.95` 使旧值主导，`DELTA=0.1` 缓慢增长，配合 `I_inhibit` 逐轮累积——抑制强度一旦上去了就很难下来。
**交给下游**：`E_final`、`I_inhibit`、`S_E`、`D_error` → 步骤 11 与 12；`w_PFC_new` → 跨轮

### 步骤 11 · policy_minimal()

**做什么**：把内部状态映射为一个行动决策。

**怎么处理**：五级 `if`，**优先级不可调**（高severity 优先于高抑制）：
```python
if event_severity > 0.8:          return "ask_clarify"
if I_inhibit > 0.7:                return "suppress"
if I_inhibit > 0.4 and severity < 0.5: return "reappraise"
if E_final[0] < -0.5 and I_inhibit < 0.3: return "express"
return "task_first"
```

**往复**：无，纯函数。
**交给下游**：`action` 字符串 → 步骤 16 写日志。不参与后续计算

### 步骤 12 · state_translator.state_to_prompt()

**做什么**：把内部数值翻译成四句自然语言，塞进固定模板。

**怎么处理`：四组独立的阈值判断，各产一句文本：

| 输出项 | 判断依据 | 两种输出 |
| --- | --- | --- |
| 感受 | `E_final[0]` | `< -0.3` → "有点被冒犯，心里不太舒服"；`> 0.3` → "心情不错，挺开心的"；否则 "没什么特别的波动" |

## 5. 三类往复机制详解

"往复"在本项目里指三类**完全不同**的结构，混为一谈会导致误判。

### 5.1 往复一 · 轮内串接（伪往复）

**定义**：同一轮内，同一个状态量被多个环节先后读写，但不跨轮。

**唯一实例**：`B` 数组
```
B（回合初）→ 步骤 3 读 B[0], B[1] 算 B_xg
             → 步骤 6 fast_path 改 B[1]（+0.3，有 clip）
             → 步骤 7 slow_path 读改后的 B
```

**为什么重要**：这构成了代码里唯一的**严格顺序约束**。若把步骤 3 挪到步骤 6 之后，`B_xg` 会用到被本轮改过的 `B[1]`，心光预算的语义就变了。

**识别方法**：这不是真的往复，只是一次"读 → 改 → 再读"。

### 5.2 往复二 · 跨轮状态往复（真往复）

**定义**：状态量通过 `st` 字典跨轮携带，依赖 `run_turn` 复用同一个 `st` 对象。

**四个候选状态量，实测无一跨轮生效** `[实测]`：

| 状态量 | 读于 | 应写于 | 实测结果 |
| --- | --- | --- | --- |
| `w_PFC` | 步骤 10 | 步骤 10（`w_PFC_new`） | 8 轮恒为 0.0 |
| `B` | 步骤 2、3、6、7、9 | 步骤 6（`B[1]`） | 8 轮恒为 `[0.5]*4` |
| `E_prev` | 步骤 9 | **无** | 8 轮恒为 `zeros(4)` |
| `M_prev` | 步骤 2（算 `x[0]`） | **无** | 恒为零向量 |
| `HabituationSignal_prev` | 步骤 2（算 `x[5]`） | **无** | 恒为 0.0 |

实测方式：包装 `pipeline.run_turn`，逐轮对比 `st` 中这五个键的前后值。完整数据见 9.2。

**维持机制**：`reset_state(seed=42)` 在会话开始时建一次，`run_session` 把它传给每一轮 `run_turn`。而 `run_scenario` 每轮都调 `reset_state`，所以**单场景单轮跑必然触发不了任何跨轮往复**。

**这是本项目最重要的结构特征** `[推断]`：所有真正体现"情绪累积"的设计都依赖跨轮。由于跨轮回写全部失效（9.2），当前版本实际上**没有任何跨轮状态演化**——每轮都在用固定的初值做单轮计算，区别只在于 `memory_graph` 与 `memory_buffer` 在累积。这解释了为什么 8 轮会话里 `D_slow` 会逐轮变化（第1 轮 0.523369→ 第 6 轮 0.699968）——那变化来自海马体匹配到越来越多的历史事件，与`E_prev`/`w_PFC` 无关。

### 5.3 往复三 · 记忆回路（跨轮，最慢但影响最大）

**定义**：对话内容 → 归档 → 召回 → 影响评估的完整闭环。

**完整时序** `[实测]`：
```
第 1~5 轮：每轮末写 buffer，缓冲区长度 1~5，不触发归档
第 6 轮：  buffer 长度达 6 → 归档 → flushed 4 条（第1~4轮）
           保留最近 2 条（第5、6轮）→ 生成 1 个 MemoryPackage
第 7 轮：  读取侧读到刚归档的包 → T24 delta 生效
第 8 轮：  buffer 长度 3，仍未达阈值 → 读同一个包
```

**关键延迟**：至少 7 轮。8 轮会话只产生 1 个归档包。

**为什么设计成这样** `[推断]`：缓冲区留 2 条不归档，是为了让归档内容有足够上下文。但代价是延迟被拉到 7 轮，对短对话场景等于无效。

**两个子回路**：
1. **语义匹配回路**（步骤 15 → 步骤 4）：本轮回写的 `danger_score` 影响下一轮海马体的 `HistoricalResidual`，进而抬高 `ReframedContext`。这条回路**不需要归档**，第 2 轮就生效
2. **记忆包回路**（步骤 17/18 → 步骤 5 → T24）：延迟 7 轮

**容易混淆的点** `[实测]`：`main.py` 走的是 `run_scenario`（每轮 `reset_state`），所以两个回路都触发不了。这就是 002 号工作里「用快照改前版本跑同一 `main.py`，输出逐行一致」的原因——T24 在那里退化为恒等变换。

## 6. 维度体系与参数归属

### 6.1 三个维度的来源与去向

T3-B 之后，**三个特征向量完全独立**：

| 名称 | 维度 | 来源 | 消费方 | 对应参数 |
| --- | --- | --- | --- | --- |
| `x` | 8 | 8 个手工标量特征 | 海马体、慢通路 | `w_s`(8)、`W_v`(2,8) |
| `x_fast` | 4 | 纯字符串启发式 | 快通路 | `w_f`(4) |
| `event_embedding` / `M` | 1024 | BGE-Large-zh-v1.5 | 海马体、慢通路 | `u_s`(1024)、`U_v`(2,1024) |

**T3-B 做了什么**：把 `m` 从 8 改成 1024，同时把 `u_s` 与 `U_v` 扩到 1024 维。`w_s` 与 `W_v` **一行未动**，因为它们乘的是 `x`，与 `M` 无关。

**解耦的意义** `[推断]`：此前 `n = m = 8` 是巧合耦合——两个不同语义的向量恰好同维，导致 `u_s` 与 `w_s` 的参数空间纠缠。解耦后可以独立调整各通路权重。

### 6.2 嵌入链路

```
raw_text
   │
   ├─► [已弃用] hash_to_8d  8 维 MD5，无语义，保留仅为 probe_embedder.py 兼容
   │
   └─► BGEEmbedder  BAAI/bge-large-zh-v1.5
                     1024 维，normalize_embeddings=True
                     懒加载，GPU 优先自动降级 CPU
                     模块级单例，避免每次 parse 重建
```

**`HashEmbedder` 与 `BGEEmbedder` 的对比价值** `[推断]`：`embedder.py` 保留 `HashEmbedder` 并要求其输出与 `hash_to_8d` 逐元素一致，这个约束让 `probe_embedder.py` 能验证两套嵌入的差异——这是评估"语义嵌入到底带来多少增益"的对照基础。

### 7.1 四个组件的职责

### 7.2 解压器的"按器官取"设计

`decompressor.py` 提供 5 个方法，体现一个设计意图：**不同器官看同一段记忆的不同侧面**。

| 方法 | 返回字段 | 谁用 |

| `for_emotion_evaluator` | `emotion_value`、`emotion_polarity` | 步骤 5（T24 用） |
| `for_danger_evaluator` | `consequence`、`evaluation`、`raw` | 未接入 |
| `for_policy` | `consequence`、`thought`、`raw` | 未接入 |
| `for_xinguang` | `keywords`、`emotion_value` | 未接入 |
| `get_fields` | 任意字段名列表 | 通用 |

**现状** `[代码]`：5 个方法里只有第一个被调用，其余 4 个都是死代码。`raw_pointer` 解析（`"1-2-3"` → `[1,2,3]`）与 `RawLog.get_many` 也因此从未被执行。

### 7.3 MemoryPackage 的双层结构

```python
# 数值层（系统用）
seq, emotion_value, emotion_polarity, keywords, raw_pointer

# 叙事层（AI 读，分标题）
narrative_cause, narrative_trigger, narrative_consequence,
narrative_evaluation, narrative_emotion, narrative_thought
```

**设计意图** `[推断]`：数值层给算法用，叙事层给 LLM 用——让记忆既能参与计算，又能被语言化。但当前主链路只用了 `emotion_value` 一个数值字段，叙事层完全未被消费。

### 7.4 归档阈值与保留策略

```
MEMORY_ARCHIVE_THRESHOLD = 6     # 攒够 6 条触发
buffer(default_keep=2)            # 归档时保留最近 2 条不打包
```

**净效果** `[实测]`：每归档一次消化 4 条，第 6 轮触发时打包的是第 1~4 轮，第 5、6 轮留在缓冲区等下一轮。若会话持续，第二次归档发生在第 10 轮（打包第 5~8 轮）。

## 8. LLM 接入与提示词构造

### 8.1 LLM 的两个调用点

| 调用点 | 位置 | 用途 | 当前后端行为 |
| --- | --- | --- | --- |
| 响应生成 | 步骤 14 | 生成 AI 回复 | 真调 DeepSeek |
| 记忆整理 | `archiver.organize_narrative` | 把对话片段打包成 `MemoryPackage` | 真调 DeepSeek，要求返回严格 JSON |

**两个调用点都在同一个 `get_llm()` 工厂下**，共享 `LLM_TEMPERATURE=0.7`、`LLM_MAX_TOKENS=512`。

### 8.2 密钥与降级

密钥来自 `secrets_local.py`（**铁律：不进快照、不进基准、不读取内容、不出现在任何文档里**）。

降级路径有三条，每条都只打一行警告就继续：
1. 找不到 `secrets_local` → MockLLM
2. `api_key` 或 `base_url` 为空 → MockLLM
3. 装了 requests 就用它，否则用 urllib 兜底

**MockLLM 的输出**：`f"[MOCK] 收到 prompt，长度 {len(prompt)}"`。

### 8.3 提示词模板

`state_translator` 产出的 monologue 是一段固定模板，末尾带 5 条硬规则：

```
【你此刻的状态（仅供你参考，不要说出口）】
- 感受：{feeling_text}
- 自控：{control_text}
- 熟悉度：{familiarity_text}
- 隐约的回忆：{memory_text}

【输出规则（必须严格遵守）】
1. 直接回应用户，用第一人称说话。
2. 禁止描述自己的内心状态。禁止使用括号、旁白、内心独白。
3. 禁止提及任何数字、分数、参数名。
4. 你的状态应当自然体现在语气、长短、用词上，而不是被说出来。
5. 若"自控"为克制状态，回应要短、要收着；若"感受"为积极状态，回应可以稍放开。
```

**设计意图** `[推断]`：第 2、3 条是为了把内部状态的影响**间接化**——不让 LLM 直接说"我很难过"，而是让它自己选择语气。这条路线的成败完全依赖第 4 条，而第 4 条无法被程序校验。

### 8.4 一处情绪表达缺口

`config.py` L24 登记：`E_final[0]` 区分度极低（-0.206 ~ -0.220），导致"感受"话术恒落在"没什么特别的波动"档。这意味着**当前版本的情绪状态在 prompt 里几乎不可见**，三场景的体验差异趋近于零。

**这不是隐私问题，是表达问题**——内部状态虽然存在，但传不到外部。根因见 8.5。

### 8.5 情绪效价轴的根本缺陷（L24 的根源）

当前 M1 的情绪系统是**"危险单轴"**，不是"正负双极轴"。

具体表现：

| 场景 | `E[0]` 实测值 | 是否符合预期 |
| --- | --- | --- |
| 被骂 | -0.207 | 负，合理 |
| 被夸 | **-0.220** | **也是负，不合理** |
| 被质疑 | -0.212 | 负，合理 |

三个场景的 `E[0]` 全在 **-0.21 附近，互相差不到 0.013**。

**`E[0]` 的物理意义是"危险/压力刻度"，不是"开心 ↔ 难过"**。所以"被夸"不可能产生正数——底层数据里根本没有"开心"这个方向。

这直接导致 `state_translator` 判"感受"时永远落在"没什么特别的波动"——它**判不出"开心"，因为底层数据里根本没有"开心"这个数**。

**这是 M3 大重构要解决的核心问题**：把效价轴从"危险单轴"改成"正负双极轴"，让被夸真的产生正效价。

**注意：这不是调参能解决的**。改阈值只会让"被骂"和"被夸"在同一个轴上一起移动，不会产生正负极性。这是结构问题，不是标定问题。

### 9.2 状态写回缺口（实测确认）

完整的状态写回应该有 5 处，**实测 8 轮会话中被改动的键为 0 个**。


| 应写回 | 代码现状 | 实测结果 |
| --- | --- | --- |
| `E_prev` ← `E_final` | 链路中无赋值语句 | **从未变动** |
| `w_PFC` ← `w_PFC_new` | 只赋给局部变量，`st["w_PFC"]` 未更新 | **从未变动** |

**`B` 的补充说明** `[实测]`：`fast_path` 确实原地修改了 `st["B"]` 的同一数组引用，机制上是通的，但 `D_fast` 始终未超过 `THETA_FAST = 0.5`，所以那个 `B[1] += 0.3` 分支从未执行。8 轮实测 `x[6]`（读 `B[1]`）与 `x[7]`（读 `B[2]`）恒为 0.500000，即 `B` 在数值上也未变化。

**`x` 的分量实测轨迹** `[实测]`（8 轮「被骂」，fixture 模式）：

| 轮次 | `x[0]` | `x[5]` | `x[6]` | `x[7]` |
| --- | --- | --- | --- | --- |
| 1–8 全部 | 0.000000 | 0.000000 | 0.500000 | 0.500000 |

`x[0]` 与 `x[5]` 恒为 0 的原因见 12.1，`x[6]`/`x[7]` 恒定的原因即上。

**严重性判断** `[推断]`：这是本项目当前最根本的实现缺口。项目全部 20 余个 `[未校准]` 参数的意义都在于调节"情绪惯性（LAMBDA）"与"自控强化（RHO）"这两个跨轮往复的强弱，而它们现在都不工作。**这意味着当前版本的行为表现无法用于评估任何参数取值是否合理**——因为参数还没有机会产生跨轮效应。

### 11.4 召回方向：放大危险 vs 习惯化削弱（T31）

T24 把召回的情绪值加进 `ReframedContext`，导致 `D_slow` 上升（实测 +0.072）。这**选择了"想起过去 → 当前危险感上升"这一方向**。

但这里有两种截然不同的解读：

- **解读 A（放大）**："这类事危险" → 想起旧事，更警惕 → `D_slow` 上升。**当前实现选的是这个。**
- **解读 B（习惯化削弱）**："经历过" → 反应反而变小 → `D_slow` 下降。

**这不是技术问题，是设计问题。**

人的反应有时是 A（一朝被蛇咬，十年怕井绳），有时是 B（见怪不怪）。系统要在两种模式之间切换，还是固定一种？

这个选择无法从技术层面推导出来——它取决于项目想要造一个"容易记住教训"的系统，还是"能够脱敏"的系统。T31 记录了这个问题，**等所有者决策**。

## 12. 本次分析新发现的问题

以下问题**未在 `config.py` 中登记**，是本次通读源码时发现的，供参考。均未改动代码。

### 12.1 `M_prev` 与 `HabituationSignal_prev` 是名义状态

**实测证据** `[实测]`：8 轮「被骂」会话，`x[0]` 与 `x[5]` 全程为 0.000000（见 9.2 数据表）。

**影响**：`x` 的 8 个分量里有 2 个恒为 0，等于只有 6 维在参与计算。海马体确实算出了 `M`，但从未喂回给编码器。

**关联**：与 L19（persons/tasks 空集）同源——`feature_encoder` 有一堆从历史里取值的分量，但历史通道全部未接通。

### 12.2 `E_prev`、`w_PFC`、`B` 的跨轮回写未生效

**实测证据** `[实测]`：包装 `pipeline.run_turn` 逐轮对比 `st` 中五个状态量的前后值，8 轮中被改动的键为 **0 个**：

```
第1轮: （无）      第5轮: （无）
第2轮: （无）      第6轮: （无）
第3轮: （无）      第7轮: （无）
第4轮: （无）      第8轮: （无）

8 轮内总共被改动的键: []

E_prev                 从未被改动
w_PFC                  从未被改动
B                      从未被改动
M_prev                 从未被改动
HabituationSignal_prev 从未被改动
```

**代码层面成因** `[代码]`：
- `run_emotion(st["E_prev"], ...)` 读 `st["E_prev"]`，但链路中无任何 `st["E_prev"] = E_final` 赋值
- `run_intercept(E_raw, st["w_PFC"])` 读旧值，`w_PFC_new` 只赋给局部变量；而 `slow_path` 用的又是 `st["w_PFC"]`（旧值）。即使想回写也没有通路
- `fast_path` 的 `B[1] = np.clip(B[1] + 0.3, ...)` **机制上是通的**（原地修改 `st["B"]` 的同一引用），但 `D_fast` 始终未超过 `THETA_FAST = 0.5`，该分支从未执行，所以 `B` 在数值上也未变

**影响**：`LAMBDA = 0.9` 的情绪惯性与 `RHO = 0.95` 的自控强化**都不生效**。多轮会话中 `E_prev` 恒为 `zeros(4)`、`w_PFC` 恒为 0.0、`B` 恒为 `[0.5]*4`。

**严重性** `[推断]`：这是设计核心与实现之间的断裂。项目所有 `[未校准]` 参数的意义都在于调节这两个往复的强度，而它们现在都不工作。**当前版本的行为表现不能作为参数取值合理性的证据**——因为参数还没有机会产生跨轮效应。

### 12.3 词库重叠检查不完整

**事实** `[实测]`：`config.py` 只 assert 了 `DANGER ∩ POSITIVE = ∅`，但 `DANGER` 与 `NEGATIVE` 存在交集：

```
DANGER ∩ NEGATIVE = {'讨厌'}
```

**影响**：`"我讨厌这个"`这类输入会同时命中危险词与负向词，`x_fast[0]` 与 `x_fast[1]` 的信号来源重叠，可能造成特征耦合。轻微但值得记录。

### 12.4 `reflex` 闭环缺一致性校验

**事实** `[代码]`：`MemoryPackage.emotion_value` 由 LLM 事后生成（0~1 浮点），而主链路的 `E_final` 是 -1~1 的向量。两套情绪口径不一致（T24 之后，前者还会通过 T24 影响后者）。

**关联**：L23 已部分记录此问题。T24 接入后，两个口径被直接串在一起，口径差异会被传导进慢通路。

## 13. 工程规范与红线

### 13.1 不可违反的红线

1. **密钥铁律**：`secrets_local.py` 不进快照、不进 hash 基准、不读取内容、不出现在任何对话或文档中
2. **禁止手抄 hash**：所有 hash 表必须由 `sha256sum` 脚本生成，且校验时用 `diff`；内嵌进汇报后要**再 diff 一次**（汇报里的手抄环节会独立出错）
3. **Windows 下 hash 采集**：必须用 shell 的 `sha256sum | cut -c1-16 | tr 'a-f' 'A-F'`，不要在 Python 里 `split()`（输出路径带反斜杠会污染 hash 前缀）
4. **不用 try/except 掩盖错误**：断言失败要如实输出
5. **参数不得擅自改动**：所有 `[未校准]` 参数即使不合理也不能在附带任务中夹带修改

### 13.2 快照规范

- 路径：`d:\aiqg\emotion_agent_snapshot_<版本>\`
- 排除：`logs`、`__pycache__`、`.pytest_cache`、`secrets_local.py`
- 排除 `logs` 的原因：`tests/test_limits.py` 会读 `logs/*.jsonl`，运行会污染测试

### 13.3 汇报编号规则（永久生效）

- 每次工作对应一个编号 `NNN`，三位数字，从 001 起按批次递增
- 单文件：`NNN.txt`；多文件：`NNN.1.txt`、`NNN.2.txt`
- 非汇报类产物（探针脚本、基准文件、快照目录）**不参与编号，保持原名**
- 每个汇报首行必须写「本文件属于 NNN 号工作」

### 13.4 版本封版流程

1. 建快照 `_snapshot_vXX`
2. 生成 `VXX_hash基准.txt`（全 `.py`，SHA256 前 16 位，字母序）
3. 三重校验：快照重算 vs 文件、工作目录 vs 基准、新基准 vs 旧基准

## 15. 分析者关注问题清单

### 15.0 三个必须先读到的判断

**判断一：当前的行为表现，不能作为参数合理性的证据。**

文档 9.2 已实测：五个跨轮状态量（`E_prev`、`w_PFC`、`B`、`M_prev`、`HabituationSignal_prev`）**全部未回写**。这意味着 `LAMBDA`（情绪惯性）、`RHO`（自控强化）这些参数**从未产生过跨轮效应**。

- 它们的不合理性，**不能用"当前表现还行"来辩护**
- 它们的合理性，**也不能用"当前表现不好"来否定**

**判断二：项目最核心的三个设计意图，只有一个是真正生效的。**

| 设计意图 | 状态 | 原因 |
| --- | --- | --- |
| ❌ 情绪有惯性 | **未生效** | `E_prev` 未回写 |
| ❌ 自控会强化 | **未生效** | `w_PFC` 未回写 |
| ✅ 记忆会累积 | **生效** | `memory_graph` + `archiver` 跨轮累积 |

**判断三：当前不是"优化"阶段，是"补完"阶段。**

系统骨架完整，但血肉不全。在**"跨轮回写"**和**"语义进入情绪计算"**这两件事完成前，**不要做任何参数层面的优化——那是浪费时间**。

### 15.1 当前唯一的重大方向：情绪评估语义化

系统有两套信号要进情绪计算：

- **语义信号**：这句话说了什么？多重？什么性质？（来自 embedding）
- **结构化信号**：谁说的？什么场合？我什么状态？（来自 `x` 其余 7 维）

**当前的问题**：embedding 有 1024 维信息，进情绪时只留 **1 个标量**（`x[0]`），且该标量因 `M_prev` 未回写而恒为 0。**语义几乎没进来。**

三条候选路线已讨论但**未选定**：

| 路线 | 效果 | 代价 |
| --- | --- | --- |
| 只改 M（保守，已做） | 记忆活了，情绪还是半聋 | 最小 |
| 路一：`x = embedding`（1024 维） | 情绪全听语义，但分不清人 | 中 |
| 路二：`x = 8 手工特征 + 1024 embedding` | 最像人，改动大 | 大 |
| 路三：`x` 保持 8 维，`slow_path` 另加 embedding 通路 | 和路二一样像人，多一个可调旋钮 | 中 |

所有者认为三条路都有缺陷，想做一次**"小重构"**——重新定义"情绪评估的输入应该由哪几部分组成"。

**三个待答问题（所有者尚未回答）**：

1. **语义信号 S 应该由哪几个数组成？**（比如：恶意程度、针对性、紧急程度…… 几个？分别是什么？）
2. **这些语义数怎么算出来？**（用 embedding 和锚点向量算相似度？让 LLM 直接打分？还是别的？）
3. **S 和 T 怎么合进情绪计算？**（加法？加权？分路？乘法？）

**这三个问题不回答，M3 大重构无法启动。**

## 16. 项目运营机制

本章记录项目的协作方式与工作流程，供分析者了解"这个项目是怎么被推进的"，以及"哪些历史约定需要遵守"。

### 16.1 三方角色

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| **所有者**（人类） | 传递信息、跑脚本、贴结果、做最终决策 | **非技术背景** |
| **开发 AI** | 按指令改代码、跑测试、如实回报 | **是施工队，不是总工** |
| **AI 顾问** | 读所有者贴来的问题，做裁决，给出下一步指令 | 开发 AI 不能自行拍板，所有裁决由顾问做出 |

**决策链**：所有者 → 转达顾问指令 → 开发 AI 执行 → 如实回报 → 所有者转顾问 → 顾问裁决。

这个机制的设计意图是**防止开发 AI 自行扩大范围或自行拍板**。开发 AI 遇到需要决策的问题（如"位置不合适要不要改公式"）时，正确做法是**先输出方案再等指令**，而不是自行判断。

### 16.2 汇报编号规则

- 每次工作一个编号 `NNN`，从 001 开始
- 单文件：`NNN.txt`；多文件：`NNN.1.txt`、`NNN.2.txt`……
- **非汇报类产物**（探针、基准、快照）**不参与编号**
